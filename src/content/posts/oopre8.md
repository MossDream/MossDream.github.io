<h1 id="OOpre课程的简单建议">OOpre课程的简单建议</h1><p>经过这学期的学习，我收获颇丰，<strong>这门课程的开设于笔者而言很有意义</strong>。</p>
<p>笔者的建议是：</p>
<font color=blue size=4 >**加大课程训练力度，可以考虑 包括但不限于 <font color=red size=4.5 >加强深入迭代、增加hack互测与博客作业形式、增加研讨课和实验课、引入上机比赛等等</font>，达到全面模拟并提前熟悉OO正课节奏的效果**</font>

<blockquote>
<p>伟大的领袖毛泽东曾说：“<strong>不打无准备之仗，方能立于不败之地</strong>。”<br>《礼记·中庸》中记载:“<strong>凡事预则立，不预则废</strong>。”<br>生活中，人们也常说:“<strong>机会都是留给有准备的人的。</strong>”</p>
</blockquote>
<p>由此可见，任何事情成功的前提便是做<strong>充分的准备</strong>，对于<strong>这门重要的OO课程</strong>也是如此。<strong>笔者衷心希望课程组能考虑这条建议</strong>。</p>
<p>下面是笔者的学习心得和过程总结，还请不吝赐教。</p>
<h1 id="代码架构分析">代码架构分析</h1><h2 id="最后一次作业代码架构">最后一次作业代码架构</h2><p>笔者用从<strong>IntelliJ IDEA</strong>导出的一张<strong>类图</strong>以供参考。<br><img src="/img/oopre8-class-diagram.webp" loading="lazy" decoding="async" alt="最后一次作业类图"><br>总体而言，这份代码基本能够<del>一次性通过历次强测</del> ，也符合<strong>checkstyle检查规范</strong>。但仍然存在<strong>诸多不足</strong>。这里浅显地分析两点。</p>
<ul>
<li>第一是<strong>类的设计问题</strong>。<em>Adventure</em>类的<strong>Adventure</strong>这个单词似乎没有很好地表达“<strong>冒险者</strong>”的意思。上一次作业原本想改，但是不想再大动干戈，避免出现其他奇怪的错误。还有<em>PrintInfo</em>这个类，原本是用来处理输出信息的，但是<strong>后来的迭代没再用到</strong>，也算是一个败笔。</li>
<li>第二个是<strong>封装性问题</strong>。对于很多的<strong>新增特性</strong>，比如背包，笔者在<em>Adventure</em>类中新增了三个属性来处理，但是应该封装成一个<em>Package</em>类更加妥当。战斗日志也可以单独封装，但笔者在<em>Main</em>类中直接对其进行处理。可以看到这样导致<strong>每个类分工不明确</strong>。</li>
</ul>

<h1 id="Jnuit使用心得">Jnuit使用心得</h1><h2 id="注解类型">注解类型</h2><p>只说说笔者用到的吧。</p>
<ul>
<li><strong>@Test</strong>：这个注释说明依附在 JUnit 的 public void 方法可以作为一个测试案例。</li>
<li><strong>@Before</strong>：有些测试在运行前需要创造几个相似的对象。在 public void 方法加该注释是因为该方法需要在 test 方法前运行。</li>
<li><strong>@After</strong>：如果你将外部资源在 Before 方法中分配，那么你需要在测试运行后释放他们。在 public void 方法加该注释是因为该方法需要在 test 方法后运行。</li>
</ul>
<h2 id="执行过程">执行过程</h2><p><strong><code>before()</code> 方法针对每一个测试用例执行，但是是在执行测试用例之前。<br><code>after()</code> 方法针对每一个测试用例执行，但是是在执行测试用例之后。<br>在 <code>before()</code> 方法和 <code>after()</code> 方法之间，执行每一个测试用例</strong>。</p>
<h2 id="测试用例">测试用例</h2><p>单元测试用例是一部分代码，可以确保另一端代码（方法）按预期工作。</p>
<p>好的测试用例有一下几个特点：</p>
<ol>
<li>已知输入和预期输出，即在测试执行前就已知。</li>
<li>已知输入需要测试的先决条件，预期输出需要测试后置条件。</li>
</ol>
<p>单元测试对测试用例有以下几个要求：</p>
<p>每一项需求至少需要两个单元测试用例：一个正检验，一个负检验。<br>如果一个需求有子需求，每一个子需求必须至少有正检验和负检验两个测试用例。</p>
<h1 id="OOpre学习体会">OOpre学习体会</h1><h2 id="面向对象编程">面向对象编程</h2><p><strong>面向对象编程</strong>（<strong>Object-Oriented Programming，OOP</strong>）是一种编程范式，它使用“<strong>对象</strong>”来设计软件。对象是包含数据（也被称为<strong>属性</strong>）和操作这些数据的方法的实体。面向对象编程的主要目标是提高软件的可重用性、灵活性和可维护性。</p>
<p>OOP有四大基本原则：<strong>封装、继承、多态和抽象</strong>。</p>
<h3 id="封装">封装</h3><p>封装是将对象的状态（属性）和行为（方法）包装在一起的过程。这使得对象的内部实现对外部是隐藏的，只有通过对象的公开接口才能访问对象的状态和行为。这样可以减少代码间的耦合度，提高代码的可维护性。</p>
<h3 id="继承">继承</h3><p>继承是一种创建新类的方式，新创建的类继承了一个已有类的属性和方法。这样，我们可以创建一种层次结构，从而实现代码的复用和扩展。</p>
<h3 id="多态">多态</h3><p>多态是指同一操作作用于不同的对象，可以有不同的解释和行为。多态可以增加代码的灵活性和可扩展性。</p>
<h3 id="抽象">抽象</h3><p>抽象是将复杂系统模型化的一种方法。在OOP中，抽象可以通过接口和抽象类来实现。通过抽象，我们可以隐藏具体的实现细节，只展示用户或者对象需要的功能。</p>
<h2 id="从面向过程到面向对象">从面向过程到面向对象</h2><p><strong>面向过程是面向对象的基础，面向对象可以说是面向过程的抽象</strong>。比如汽车有开车，加减速和刹车，关于汽车的操作有好多，每一个都需要一个具体的过程来实现，把这些过程抽象的总结起来就可以形成一个类，这个类包括的汽车所有的东西，所有的操作。</p>
<p><strong>面向过程是具体化的</strong>，流程化的。解决一个问题，需要一步一步分析需要怎样，然后需要怎样，一步一步实现的。<strong>面向对象是模型化的</strong>，抽象出一个类，这是一个封闭的环境，在这个环境中有数据有解决问题的方法，你如果需要什么功能直接使用就可以了，至于是怎么实现的，你不用知道。</p>
<p>从代码层面来看，面向对象和面向过程的主要区别就是<strong>数据是单独存储（结构体）还是与操作存储在一起（类）</strong>。</p>
